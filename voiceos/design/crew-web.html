Design brief: crew

for pasting into a design session

Context for a design session. This page describes the product, the concepts the screens show, what has been decided and why, and what is still open. The prototype behind it is example data; nothing here is wired to crew.

The product

crew is a workspace manager for coding agents, mainly Claude Code. A developer often works on several features at once, each spread over a few repositories (a web front end, an API, a worker). crew gives each feature its own isolated copy of every repo it needs, starts their development servers on stable ports, and wires the repos to each other (the front end's API URL points at this copy's API, not another one). Then it launches a Claude session in that copy.

Today crew is a command-line tool with a terminal UI (TUI). The direction now: crew starts a local web server by itself, and a web UI replaces the TUI. Every action keeps a command-line form (agents drive crew through commands), and the web UI only ever runs those commands.

Voice OS is crew's other half, already built: a web page that runs one Claude Code session per worktree and lets the developer drive all of them by talking (or typing, or clicking). A small model routes speech to the right session; sessions answer in short spoken lines, ask questions, ask for permission and report when done. It is dense on purpose: it is the everyday workhorse, open all day.

The users are developers who run several Claude sessions in parallel, often across more than one machine (a laptop plus a VM or build box). They are comfortable with git and terminals, and want to see state at a glance without clicking around.

Concepts

Project
One git repository crew knows, on one machine: where its checkout is, how to install it (bun install), which dev servers it has (web, api, worker) with their commands, and its bindings. Added from a git URL (crew clones it) or a folder the user already has (crew adopts it in place).
Workspace
A set of projects worked on together, e.g. store-front + checkout-api. Pure membership: each project is in worktree mode (its own copy, the default) or direct mode (the user's own checkout, as it is). A project can be in several workspaces.
Worktree
One working copy of a workspace: a git worktree of every project, on its own branch (crew/<workspace>/<worktree>/<project>), with its own reserved ports. Named store-front/main, store-front/search-filters. This is what a Claude session works in, and what Voice OS shows as a session.
Dev server
A process a project runs during development (web on :3000). crew gives each worktree its own ports, so two worktrees of the same workspace run side by side.
Environment
The variables crew sets for a project in every worktree (called bindings in the CLI today). Each value comes from somewhere: another project's URL or port in the same worktree (CHECKOUT_URL → checkout-api's URL, which is how a worktree's projects find each other and not another worktree's), the worktree's name, or a fixed value. It can apply to every server of the project or just one.
Pinned value
A variable fixed for one worktree only (an override in the CLI). It wins over the project's environment: a test key in one worktree, debug logging in another.
Machine
Where projects live. This Mac runs crew and the web server; other machines (a VM, a build box) are reached over SSH, each with its own crew and its own projects.
Check
crew check project: crew rebuilds a project from nothing (clean checkout, install, start its servers, see they answer). A project is ready when its check passed. This is the proof of "set up", not anyone's say-so.
Setup session
One persistent Claude Code session per machine, always on. It lives only in Setup: Voice OS does not show it or talk to it. Setting up a project, fixing a worktree or adding a machine are new topics in its one conversation, so it remembers what it did; Its job is crew itself: it reads a repo, works out its install and dev servers, asks the developer only what it can't know (a REDIS_URL), records it with crew commands, and runs the check until it passes.

How it fits together

  1. crew is the product. Running crew starts a local web server (and replaces the terminal UI). Its web UI has two halves: Voice OS, for working, and Set up, for configuring. Both are served by the same server; remote machines are reached through it over SSH.
  2. Opening. On black with a faint glow from below, the crew wordmark (system type, tight tracking) fades up, then one line under it ("your sessions, every machine"), and it dissolves into Home. About 2.5 s, once per load, skipped with reduced motion. No rings, no coloured bars: restraint over spectacle.
  3. Launcher (Home). The crew wordmark and "What would you like to do?", then two frosted cards: Voice OS ("Talk to your sessions on every machine", with "4 active · 1 waiting on you") and Set up ("Projects, workspaces and machines", with "2 projects need setup"). The last choice is outlined and focused, so Enter goes straight in; "Always open Voice OS" skips it next time. Home in either half brings the launcher back. There is no separate home page.
  4. First run. With nothing set up, the Voice OS card is greyed out and unclickable ("Set up a project first: your sessions live here once you have one"), and Set up is outlined with "start here".
  5. Choosing Voice OS plays a short moment (about 1.5 s): "Voice OS" fades up as a wordmark, set like crew's own (no icon), then it dissolves into Voice OS. Choosing Set up opens Setup directly.

Voice OS, the workhorse

Open all day, dense on purpose, full width. Its content stays flush and boxy: panes split by hairlines, bordered lists, no cards floating on a lit background. Both bars are docked too: a flat top bar and a flat voice bar, each split from the content by a hairline.

  • The top bar carries the active sessions. A bar docked across the top, split from the content by a hairline: the crew mark (Home), Active, then one tab per active session with its state dot (and its machine when it's not This Mac). The last tab is +: it opens Activate, every worktree on every machine in one list, grouped by machine then workspace, with a search field and a machine filter (All machines, This Mac, Build box…). Each machine heads its group with its state ("4 of 6 active", or "not reachable · last seen 2h ago" with its rows dimmed). Activate starts that worktree's Claude: it gets a tab and an idle row in Active, with no page change. Worktrees are made in Set up, not here. On the right: Claude usage. No sidebar.
  • Active (where Voice OS opens): one list of the active sessions, one full-width row each, every row carrying its own status (asked you, running, done, idle). No separate "waiting on you" alert; a session that asked shows it in its row and its tab dot.
  • The session page keeps today's layout at full width, with what a real Claude session streams: your words in white semibold after ›, Claude's replies as rendered markdown (paragraphs, lists, inline code, tables), each tool call as an amber ▸ line ("run bun test catalog", "start a subagent: …"), failures as red ✕ lines, diffs, asides (a side question and its answer), screenshots inline, doc cards. Panels on the right: Session, Sub-agents, Dev servers with links, Voice, Docs, Elsewhere, Where.
  • The voice bar is docked across the bottom, like the top bar: the last spoken line, the mic, where your words go, the listening mode.
  • A machine's worktrees are a library by workspace, inactive ones dimmed with Activate, and a link to set the machine up.
  • Settings (the gear, far right): listening mode, the two keys (checked before saving; a rejected one is red with what to do), Discord (connected, status, turn off; the four setup steps when it isn't), session names, and the machines with their crew version (a reachable remote behind is updated by this Mac; an unreachable one says when it was last seen).
  • Listening mode is also a menu at the right of the voice bar: Hands-free (a pause ends your turn), Push to talk (hold Space or the mic), Dictation (words fill the field until "send"). The field's hint follows the mode.
  • Moments show as one row above the spoken line, with the answers as buttons and what to say: "Sent to checkout. Switch there?", "For checkout?", "admin/main isn't active. Activate it?", "store-front/main is working. Deactivate anyway?", and the meanwhile line read once it's quiet, with a button per session it names.
  • Session states are one row under the session header: a question with its options as buttons ("say one, two, or the option's name"), a remote that dropped ("reconnecting · your words wait here"), a crash ("Claude stopped unexpectedly · nothing you said was lost", Restart; no log button, since Voice OS keeps no per-session log to show). Words for an inactive worktree wait in its queue, shown on its Activate row ("1 waiting: …").
  • On Discord: "Voice via Discord" in the top bar, the mic becomes a Discord badge, the field shows what you say as you speak, the mode menu goes away. No take-back button: leaving the channel brings audio back to the page.
  • Empty and lost: Active with nothing active offers "Activate a worktree". If crew's server stops, a banner under the top bar says so and how to start it, on both halves; it clears itself on reconnect. Setup's Settings shows a new crew release with Update (Voice OS keeps running on the old one until you restart it).
  • Phone: one column; the tabs scroll; usage, the route chip and the mode menu step aside (the mode stays in Settings); panels stack under the stream; the voice bar stays docked.

First-time onboarding

As small as it can be: pick projects, then talk. crew starts its server and opens the browser; after the opening, the first-run Home has Voice OS greyed ("Add a project first") and Set up marked "start here".

  1. Pick your projects. Git checkouts found in the usual code folders, ticked, each with its path and remote; crew records where they are and changes nothing. Or add by URL or path, or import from another machine.
  2. Make a workspace. A name (the first project's by default) and which of the added projects run together (the first one ticked). Create runs the add-worktree pipeline in place: per project, checkout on its crew branch, .env copied, install from the lockfile; then "servers: none yet". The others wait on the board.
  3. Then Voice OS. "Open Voice OS" (or "Go to the board"). The first time: allow the mic, paste the Soniox and Anthropic keys (they stay on this Mac; Setup never asks for them). Start plays the Voice OS moment and lands on the workspace's main session, the only tab. Claude says it can read, change and test the code now, and that running the app needs dev servers ("say set up the dev servers"). The side panel says "Dev servers: not set up yet · Set up".

Not finished is state, not a prompt. Setup never nags or blocks: the board shows one quiet strip row ("3 projects not set up · no install or dev servers yet") with Set up with Claude, and each project row says Set up in its State column. Voice OS raises it only when it matters: asked to run or try something with no servers recorded, the session says so and offers to work them out.

Taught later, each when first needed: remotes, the proxy, Discord, names and pinned values. Finding projects is a bounded scan of the usual folders (~/code, ~/projects, ~/dev, ~/src, ~/Developer…), two or three levels deep, never ~/Documents, Desktop or Downloads (macOS would show a permission prompt); it lists checkouts and never analyzes them. Worktrees, not direct mode, even here: the session never edits the folder you have open.

Setup, the part to design

Job: get projects, workspaces and machines into a state where every worktree's servers run, and keep them there. The developer should see the state of everything on one screen, and do common things in one click.

  • One machine at a time. Each machine has its own projects, workspaces and setup session, so Setup shows one machine, picked from a menu right after the crew mark in the toolbar (with Machine settings and Add a machine in the same menu). Everything added goes to that machine; the breadcrumb trail starts with its name.
  • The board is a table. Projects: a row each with install, dev servers, workspaces and state (ready, check failed, or Set up / Ask Claude). Workspaces: a row each with its projects and its worktrees as pills coloured by their servers, plus + new.
  • Projects | Workspaces switch the table; the add button follows (Add project / New workspace).
  • "Environment" and "pinned values", not "bindings" and "overrides". Both set environment variables; the UI says where each value comes from ("checkout-api's URL", "the worktree's name", "fixed") and what a worktree actually gets, instead of naming the mechanism. "Connections" was considered and dropped: not every variable connects to something.
  • Setting a project up is yours or Claude’s. A form holds every part (install, env command, dev servers, environment), prefilled with what crew detects in the repo, and shows the commands it will run; Save and check runs crew’s check. Or hand it to the setup session, which fills the same things in and asks you only what it can’t work out. Either way the check decides "ready". Its sessions can already work on the code before setup finishes; only dev servers wait. So "needs setup" is a quiet state, not an error.
  • A worktree is created when its servers answer. New worktree checks out, installs and starts every server, showing each come up. If one fails, the setup session takes over in place with the log ("checkout-api needs STRIPE_KEY: copy it from main and restart?").
  • One Claude chat per machine, on its board. A "Setup with Claude" card sits at the top of each machine’s board. When Claude is working or waiting on you, it says so with Open; when it is free, it has a field to ask anything. Every "Fix with Claude" or "Ask Claude" button in Setup sends its request there: if Claude is free you land in the chat with the request filled in, ready to send or edit; if it is busy, you can queue the request or open the chat, never interrupt it. There are no per-project or per-worktree Claude sessions. Problems carry two buttons: Fix (the page with the fix) and Fix with Claude.
  • The setup session is parsed, not just printed. Claude’s output is drawn the way Voice OS draws a session stream: your words in white semibold after ›, what Claude says as plain text, each step as an amber ▸ line, every crew command followed by a green "✓ recorded" line saying what it recorded, and its questions as answer cards (options with a line each, plus "Something else…"). The chat is a general Claude session, so it has no side panel about one project: crew’s own state (recorded config, check results, dev servers) lives on the board and the project, workspace and worktree pages.
  • Every form shows the command it runs (crew add project payments https://…), updated as the developer types. The UI never does what the command line can't.
  • Remote machines are first-class: pick one in the toolbar and everything is the same, configured by that machine's own setup session.

When something fails

  • One strip of problems above the board, for the machine on screen (the machine menu says when another one needs you): a failed check, a dead dev server, a project not set up yet (quieter). Each opens the page that has its fix.
  • The table says what failed ("check failed · install"), the worktree pill says which server died. Red is only for things that need the developer.
  • Every failure page has the same block: what failed and when, the step it stopped at, the last lines of the log, one sentence on why, then the ways out: fix with setup (Claude), edit setup by hand, check again, full log.
  • A failure never breaks what works: the project stays as it was set up, worktrees keep their code, and the other machine stays ready.

Decisions so far, and why

  • The terminal UI keeps one job: launching Claude sessions. Everything it does today for configuring (projects, workspaces, worktrees, checks, settings) moves to this web Setup. Afterwards the TUI only picks a worktree and starts Claude in the terminal, the editor with Claude, or a shell.
  • Setup is separate from Voice OS. Configuring is crew's job and needs no voice; keeping it out of the workhorse keeps Voice OS quiet. Both are served by the same local server.
  • Calm, but never at the cost of visibility or clicks. An earlier "one thing per page" version hid state (Build box's broken project was invisible from This Mac) and took four clicks to add a project. The table shows every project on a machine at once (0 clicks), adding a project and starting its setup is 1, and switching machine is 2.
  • A table over cards and lanes, scoped to one machine: dense, scannable, every project's state visible without a click. An all-machines matrix was tried and dropped: setup is per machine.
  • Claude helps, it is never the only way. Everything has a form. The setup session is offered beside the form for the fuzzy parts (secrets, databases, tool versions), and can take over from a half-filled form.
  • Onboarding installs, but sets up no dev servers. Making the first workspace runs the add-worktree pipeline: checkout, .env copied, the install picked from the lockfile, so its session can run the tests at once. An install that fails is shown with Fix with Claude and Retry, and never blocks carrying on; dev servers come per project in Set up.

Visual language

Refined against Apple's Human Interface Guidelines: depth comes from layers and materials, not from outlines.

  • Two layers. The content layer holds the board, lists and forms on grouped surfaces lifted by fill (#111316, then #1b1e23 for fields, #24282e for selected), separated by inset hairlines (white at 7%). The functional layer (top bar, toasts, later sheets) is a translucent material: blur 24px, saturation 1.4, a faint highlight edge and a scroll-edge fade where content meets it. Never glass on content.
  • Ground: true black, lit far back by two soft, low glows (a faint white top-left, green top-right) so the material has colour to pick up. Voice OS keeps its own dark slate (#0e1116).
  • One colour, one meaning: no brand hue: focus, links and your own words are white or near-white (set apart by weight and the › mark), so the page doesn't read as an AI product; amber only for "in progress"; green for ready and listening; red for needs you or failed. Red appears as tinted fills, never outlines or edge bars.
  • Labels: primary #f2f5f8, secondary 66% and tertiary 50% white; nothing below 4.5:1 on black, small labels at least 11px.
  • Type: the system font everywhere, titles and the wordmark included (-apple-system, SF Pro, Segoe UI); the system mono (ui-monospace, SF Mono, Menlo) only for steps, refs, ports, commands and logs. No web fonts: the page loads nothing from outside.
  • Controls: filled, not outlined; at least 28px tall. One white primary action per view. Segmented controls are a filled track with a raised selected segment.
  • Motion: pages and sheets arrive with a short rise and blur (0.45s); the opening and Voice OS moments are the only dramatic ones. Reduced motion, reduced transparency (opaque bar) and increased contrast (stronger edges) all have an answer.
  • Top nav is a floating toolbar as wide as the content, in the material: the crew mark, then the breadcrumbs right beside it, actions on the right. Breadcrumbs follow the structure (Setup › Workspaces › store-front › main), not the click history; every level is a click away, and Esc goes up one.

Rules the design must keep

  • Every action maps to one crew command; show it where it helps trust.
  • "Ready" comes from crew's check, and step lists come from crew's records, never from what Claude said.
  • Nothing is deleted without asking; removed checkouts go to a trash, never deleted inline.
  • Example names are generic: store-front, checkout-api, signals, admin, infra-ops, payments.
  • Works at phone width (the table scrolls sideways inside its box; the page never does).

Open questions

  • Whether problems on other machines should show a badge on the machine picker (they do in the menu: "Build box · 1 needs you").
  • How the table scales to 20+ projects: collapse ready rows, or filter to "needs you"?
  • Where the setup conversation lives: its own page (now), a sheet over the board, or a side panel that stays while the board updates.
  • Should a new project get its own workspace by default (the form defaults to yes)?
  • Environment: should the workspace view draw which project reaches which (store-front → checkout-api)?
  • The CLI keeps binding and override working; friendlier names next to them (crew add env, crew pin) are a separate decision.
  • Editing a project by hand (servers, install) or only through the setup session.
  • How the first-run onboarding (pick the projects found on this Mac) hands over to this board.
  • Whether "nothing set up" (which greys out Voice OS) means no project or no worktree yet.
  • crew without a browser: on a remote reached over plain SSH, the command line stays the way in.
